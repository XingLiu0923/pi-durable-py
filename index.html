先认清五种记录

同一个会话里，请求的处理结果、消息内容和执行进度各有对应记录。记录通过 ID 或文档地址连起来。

Conversation
这段对话的归属范围。
其他记录用 conversation_id 指向它。
Submission
一次输入处理到哪了，回答在哪里。
entry 指向输入，answer 指向回答。
Entry
已经写下的一条消息。
用户问题、模型回复、工具结果。
Task
一项工作执行到哪一步。
state 保存状态和 checkpoint；结束后保存 outcome。
Document
会话的配置和可变状态。
kind 指明用途，key 指明属于谁。

pi.agent 保存模型与工具配置 · pi.live 保存当前 run 和进度 · pi.inbox 保存排队输入 · pi.usage 累计用量。

页面的 _live 是 Scheduler 在内存里的未结束任务索引，_docs 是 Document 缓存。它们根据存储记录建立；Invocation 保存一次调用的代码引用和异步执行信息。

发生了什么

  1. 为会话保存配置

    先创建会话 #1，并同时保存它的 pi.agent 配置。c:1 表示这份配置属于会话 #1，里面指定用叫 fake 的模拟模型。

  2. 接收输入，再启动任务

    同一批写入会记录请求回执（Submission #2）、用户消息（Entry #3）和待执行的 Task #4。Scheduler 先把任务写成 running，再真正开始执行。

  3. 保存答案，结算 Submission

    模型给出回答后，框架保存回答，把 Submission #2 标成 done，并更新 Task 状态。之后，沿着回执的 entry 和 answer 两个字段，就能分别找到原问题和回答。

组件时序图

虚线是组件调用。指向 DB 的实线是一批存储写入，点开可按表查看字段变化和写入的 JSON。

数据来自 Python 教学版的一次运行，使用模拟模型和 MemoryStorage。DB 表示存储层。组件调用由代码和写入顺序还原，运行状态只在提交发布时采样。

Scheduler 先预留任务，再启动 Invocation

_reserve() 内部等待提交成功才返回，_start() 再将 Invocation 放入内存索引。第 3 次提交发布时，可以在图里看到 running 的任务和空的 _invocations。
