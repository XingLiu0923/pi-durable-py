全局速查：五种记录、引用关系与 Task 状态机

同一个会话里，请求的处理结果、消息内容、执行进度和可变状态分别落在五种持久化记录中，靠 ID 与文档地址连成一张图。

Conversation
这段对话的归属范围。
其他记录用 conversation_id 指向它；子会话用 owner 挂到父 Task。
Submission
一次输入处理到哪了，回答在哪里。
entry 指向输入，answer 指向回答；状态为 queued / placed / done / unanswered。
Entry
已经写下的一条不可变消息。
用户问题、模型回复、工具结果；永不修改，按序追加。
Task
一项持久化状态机的执行进度。
state 保存状态与 checkpoint；结束后保存 outcome；restarts 与 abort_requested 支撑恢复和中止。
Document
会话的配置和可变状态。
kind 指明用途，key（如 c:1）指明作用域。

pi.agent 保存模型与工具配置 · pi.live 保存当前 run、流式进度和工具槽位 · pi.inbox 保存忙时排队输入 · pi.usage 累计用量。

页面左侧的 _live 是 Scheduler 在内存里的未结束任务索引，_docs 是 Document 缓存，它们都由存储记录重建；Invocation 保存正在执行的异步调用及其模式（run / abort）。

发生了什么

  1. 意图落盘，紧接着进程暴毙

    第 7、8 次提交里，两个工具都已提交 execute checkpoint（附带各自的 replay 策略），第 9 次提交还把扣款的部分输出刷进 pi.live。随后进程直接崩溃，没有任何关闭写入，DB 留下 running 的 #6、#7 和 waiting 的 #4。

  2. 新进程 open() 恢复，并幂等承接请求

    第 10 次提交由新进程的 Harness.open() 触发：只把崩溃时处于 running 的 #6、#7 改回 pending 并把 restarts 加 1，waiting 的 #4 保持 restarts: 0。新进程用同一个 request_id 重发 submit()，直接命中原 Submission #2。

  3. safe 重跑，unsafe 带着部分输出安全中断

    重开后两者直接进入 execute 阶段：第 12 次提交 fetch_page（safe）重跑成功写入 Entry #8；第 13 次提交 charge_card（unsafe）绝不重跑，而是把崩溃前落盘的部分输出拼进 interrupted 错误结果写入 Entry #9，再交给模型总结回答。

恢复专用的 execute_phase：按 replay 决定重跑或中断

正常流程不会进入 execute_phase；只有进程在意图提交（第 7、8 次）和结果提交之间崩溃，新进程在第 11 次提交重新领走任务时才会执行到这里，分别产生第 12、13 次提交。
