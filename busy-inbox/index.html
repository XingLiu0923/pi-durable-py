先认清五种记录

同一个会话里，请求的处理结果、消息内容和执行进度各有对应记录。记录通过 ID 或文档地址连起来。

Conversation
这段对话的归属范围。
其他记录用 conversation_id 指向它。
Submission
一次输入处理到哪了，回答在哪里。
entry 指向输入，answer 指向回答。
Entry
已经写下的一条消息。
用户问题、模型回复、工具结果。
Task
一项工作执行到哪一步。
state 保存状态和 checkpoint；结束后保存 outcome。
Document
会话的配置和可变状态。
kind 指明用途，key 指明属于谁。

pi.agent 保存模型与工具配置 · pi.live 保存当前 run 和进度 · pi.inbox 保存排队输入 · pi.usage 累计用量。

页面的 _live 是 Scheduler 在内存里的未结束任务索引，_docs 是 Document 缓存。它们根据存储记录建立；Invocation 保存一次调用的代码引用和异步执行信息。

发生了什么

  1. 工具执行时，两条输入先入队

    第 8、9 次提交时，build 工具仍在执行。两条输入分别建成 queued 的 Submission #7（steer）和 #8（followUp），内容先写进 pi.inbox，还没有用户 Entry。

  2. 工具结束，steer 加入本轮

    第 13 次提交在 postTools 边界取出 #7，写成用户 Entry #12，把 #7 改成 placed。新的 generation Task #13 接手当前 run，同时处理原始输入 #2 和追问 #7。

  3. 本轮回答后，followUp 开启下一轮

    第 16 次提交写入回答 Entry #14，把 #2 和 #7 都结算为 done；同一批写入也将 #8 变为 placed，创建用户 Entry #15 和下一轮的 Task #16。第 19 次提交才写入 #8 的回答。

在两个处理时机挑选队列项

这段逻辑决定从 pi.inbox 拿哪些项。示例的 postTools 阶段只取出 steer；源码也指出，若队列里有 reset，这个阶段也会挑选 followUp。
